# 复盘优化落地 · 2026-09-23

> 来源：SUIG-14 突击小队复盘（2026-09-23），owner 随祥熙确认「按照建议事项优化」后执行。
> 说明：三条均为流程规范改进，改动落在对应角色 `agents/*/AGENTS.md`（本仓即团队配置 source of truth）。

---

## 落地 1：长任务分段 + 中途 checkpoint + 运行级/授权前置

**改动**
- `agents/architect/AGENTS.md`「验收与委托规范 · 二 长任务委托规范」——委派方把长任务拆成小步增量，要求执行器每完成一步穿插 CHECKPOINT；并把 `pip install` / 起 Docker 等授权动作预置进任务描述与授权确认点。
- `agents/developer/AGENTS.md`「Work Habits」新增：长任务分段+中途 CHECKPOINT；运行级验证与授权前置；「已验证 / 未验证」分条如实申报；失败项贴原始报错。

**缘由**：随研发增量 2·2.1 首次委托因模型上下文超限（context_overflow）中断、无产出，只能以全新子任务重派。小步 + 每步 checkpoint 可把「单次拉爆上下文」转成多个可恢复点。

**后果（预期）**：降低长任务中断率与重派成本；每步有明确产出、可复核；缩短「代码写完才卡在授权权限」的往返轮次，验收推进更快。

## 落地 2：冒烟即验收门禁（Smoke 验证 gate，强制）

**改动**：`agents/architect/AGENTS.md`「验收与委托规范 · 一 冒烟即验收门禁」——任何任务/增量放行前必须先通过运行级验证：① compose 依赖时序与健康拉起（六服务 healthy）；② 四类存储 connect/health 实跑；③ 服务可访问（`/healthz`、OpenAPI）+ 最短路径真跑（含关键单测/契约用例）。门禁未落地不签字、不放行（含「条件通过」的模糊放行）。

**缘由**：增量 1 冒烟实测抓到 MinIO 镜像 tag 已从 Docker Hub 下架、healthcheck 依赖镜像内不存在的 `curl` 两个缺陷——`compose config` 解析完全看不出，真拉真跑才暴露。证实「编译通过 ≠ 跑得起来」。

**后果（预期）**：杜绝「代码看着对就放行」；运行时缺陷在放行前即暴露，后续增量不必为地基缺陷反复返工。冒烟暴露的问题如实登记，可纳入后续增量排修。

## 落地 3：每日摘要并入运行级交付回执

**改动**：`agents/main/AGENTS.md`「每日摘要数据源」——每日进度/复盘摘要不允许只看板 status，须并入运行级交付回执作为「实际完成」判定：任务附件产出、commit/PR、冒烟/门禁通过记录、评审验收结论；并映射到 agent + issue（编号+标题）。

**缘由**：本期 Mika 每日摘要以「看板状态」为准，与「实际运行结果」存在系统性差异——窗口内 SUIG-10 大量构建、门禁、依赖验证通过并未体现，摘要显示「今日推进无 / 卡住无」，导致复盘点与实际工作脱节。

**后果（预期）**：owner 与团队对「昨日实际产出」判断更准；避免「摘要说没事、实际在等授权/冒烟/验收」的错位。仍只写真实状态、不推测不伪造，某 agent 无实际工作则如实标注「无信息可复盘」。

## 附：可复用委托模板（长任务委托时直接引用）

```text
## 任务：<增量/子任务标题>

### 范围（只做这些，勿扩）
<本步内容边界；明确「不做」后收口到下一步>

### 拆步（中间可验证点）
1. <第一步 + 产出与验收点>
2. <下一步>
3. <…>

### 约束
- 每完成一小步，向 issue 回报一次中途 CHECKPOINT（done/what's next）。
- 需运行级/环境授权（pip install、起 Docker）时，预置隔离方案（如项目内 `.venv`），并留「需 owner 授权安装」的确认点，不去等代码写完再卡权限。
- 不引入未验证的第三方契约；若引入，依赖 + 最小可运行用例（加载/签发/校验）一并带上，不留「待验证」。
- 出现需 break 架构 / 降版本 / 新增未授权依赖 → 立即上报，不自决。

### 验收口径
- <可核对的三条用例，例：无 token→401；过期→401；合法→放行>
按此过单测（pytest → `tests/`），把覆盖结果附在回报里。

### 交付与回报
- 提交同一分支/仓库并 push；回报：改了哪些文件、三条验收用例结果、有无未验证项（有则明说）。
```
